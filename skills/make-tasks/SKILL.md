# Make Tasks (Создание задач)

Превратить одобренный `implementation-plan.md` в атомарные задачи, каждая из которых выполняется независимо одним разработчиком или агентом. Задачи сохраняются отдельными файлами в поддиректории `tasks/` директории фичи.

## Приоритет источников

При формировании задач источники используются в следующем порядке приоритета:

1. **`implementation-plan.md`** — главный источник: декомпозиция, последовательность, зависимости, библиотеки
2. **`functional-spec.md`** и **`ui-spec.md`** — закрывают пробелы и неясности плана: контракты, состояния, поведение
3. **`feature-spec.md`** — контекст и первоначальная постановка задачи; используется для понимания «зачем», не для переопределения плана

## Роли

- **AI-агент** — генерирует задачи на основе плана и спецификаций
- **Человек** — проверяет и при необходимости корректирует задачи

## Критерий готовности

Задачи достаточно детальны, чтобы разработчик (или агент) мог выполнить каждую без дополнительных уточнений.

## Процесс

### Шаг 1 — Собрать входные документы

Прочитать в порядке приоритета:
- `implementation-plan.md` — **обязательный вход**
- `functional-spec.md` и `ui-spec.md` — если существуют
- `feature-spec.md` — если существует

Если `implementation-plan.md` отсутствует — сообщить пользователю и остановиться. Без одобренного плана задачи не создаются.

Уточнить у пользователя путь к директории фичи, если он неочевиден. Задачи будут сохранены в `<директория фичи>/tasks/`.

### Шаг 2 — Составить список задач

Для каждой единицы работы из плана создать одну задачу. Правила разбивки:

- Одна задача = один атомарный результат (файл создан, контракт реализован, экран работает)
- Если единица работы слишком крупная (условно > 4 часа) — разбить на подзадачи
- Если несколько единиц работы неразрывно связаны и не имеют смысла по отдельности — объединить в одну задачу
- Сохранять нумерацию и группировку блоков из плана

Составить плоский пронумерованный список задач с короткими названиями — для согласования с пользователем на шаге 4.

### Шаг 3 — Наполнить каждую задачу

Для каждой задачи заполнить все разделы шаблона (см. `references/task-template.md`):

**Название** — короткое, содержательное, начинается с глагола действия («Реализовать», «Добавить», «Настроить», «Удалить»).

**Описание** — 2–3 предложения: что это, зачем нужно, в каком контексте.

**Что нужно сделать** — пронумерованный список конкретных действий. Ориентир для разработчика: что именно изменить или создать, какие контракты соблюсти, на какие разделы спецификации опираться.

> Важно: не программировать. Описывать ЧТО, а не КАК. Фрагменты кода допустимы только если без них невозможно однозначно описать суть (например, сигнатура метода из контракта functional-spec). Решение о конкретной реализации принимает разработчик.

**Definition of Done** — список проверяемых условий завершённости. Можно ссылаться на конкретные пункты приёмки из `feature-spec.md`.

**Acceptance Criteria** — наблюдаемое поведение с точки зрения пользователя или вызывающего кода: «при X происходит Y». Формат: `- [ ] Если … то …` или `- [ ] [действие] → [результат]`.

**Зависимости** — номера задач, которые должны быть завершены до начала этой. Если зависимостей нет — написать «Нет».

Формулировка задачи должна быть полностью самодостаточна без чтения `implementation-plan.md` и/или спецификаций

### Шаг 4 — Представить на согласование

До записи файлов вывести пользователю:
- Итоговый список задач: номер, название, зависимости (одна строка на задачу)
- Общее количество задач
- Задачи на критическом пути

Спросить: «Всё верно? Или скорректировать состав / границы задач перед записью?»

Записывать файлы только после подтверждения.

### Шаг 5 — Записать файлы задач

Создать директорию `<директория фичи>/tasks/` (если не существует).

Для каждой задачи создать файл по имени:

```
tasks/task-NNN-short-name.md
```

где `NNN` — трёхзначный номер с ведущими нулями (001, 002, …), `short-name` — транслитерация или английское краткое название задачи в kebab-case.

Использовать шаблон из `references/task-template.md`.

После записи вывести список созданных файлов и одно предложение: сколько задач создано и каков критический путь.

## Язык

Общаться с пользователем на русском. Файлы задач писать на русском. Технические термины, идентификаторы, имена файлов, команды и код внутри блоков кода — в оригинальном виде (английский).

## Ограничения

- Не коммитить изменения
- Не выводить commit message
- Не начинать реализацию задач
- Не пересматривать решения из `research.md` и `implementation-plan.md`
- Не редактировать входные спецификации и план
- Не добавлять требования, не обоснованные входными документами
