# Review Plan (Обзор плана реализации)

Проверить `implementation-plan.md` на полноту, отсутствие избыточности и адекватность. Результат — файл `implementation-plan-review.md` с классифицированными замечаниями.

Это итеративный процесс. После каждой итерации план дорабатывается до тех пор, пока не останется критических замечаний.

## Роли

- **AI-агент (ревьюер)** — проводит автоматические проверки, формирует файл замечаний
- **AI-агент (исправитель)** — устраняет выявленные недостатки в `implementation-plan.md`
- **Человек** — принимает итоговое решение: «план хорош» или «вернуть на доработку»

## Что проверяется

### Критерий A — Покрытие критериев приёмки

Для каждого критерия приёмки из `feature-spec.md` убедиться, что в плане есть одна или несколько работ, явно его реализующих.

Фиксировать: критерии без соответствующих работ в плане.

### Критерий B — Отсутствие избыточных работ

Для каждой единицы работы в плане убедиться, что она обусловлена требованием из `feature-spec.md`, `functional-spec.md` или `ui-spec.md`.

Фиксировать: работы, не имеющие обоснования в спецификациях (оверинжиниринг, «на вырост», не запрошенные улучшения).

### Критерий C — Покрытие требований из functional-spec и ui-spec

Для каждого контракта, модуля и потока данных из `functional-spec.md` убедиться, что план содержит соответствующую работу.

Для каждого экрана и состояния из `ui-spec.md` убедиться, что план содержит соответствующую работу.

Фиксировать: требования из производных спецификаций, не покрытые планом.

### Критерий D — Конфликты с существующим кодом

Прочитать файлы кодовой базы, затрагиваемые планом. Проверить:
- Не дублирует ли запланированная работа уже существующую реализацию
- Не конфликтует ли новая логика с существующими интерфейсами, типами или контрактами
- Не создаёт ли план несовместимых изменений в одних и тех же файлах

Фиксировать: каждый конфликт с указанием файла и конкретного места в коде.

### Критерий E — Корректность последовательности и зависимостей

Проверить:
- Зависимости между блоками работ указаны явно
- Последовательность логична: ни одна работа не ссылается на результат работы, стоящей позже неё
- Параллельные потоки не имеют скрытых взаимных зависимостей
- Нет циклических зависимостей

Фиксировать: нарушения порядка, неуказанные зависимости, конфликты параллельных потоков.

## Классификация замечаний

Каждое замечание получает одну из меток:

- **[КРИТИЧНО]** — блокирует реализацию или приведёт к неверному результату; план нельзя принять
- **[ВАЖНО]** — снижает качество или полноту, но не блокирует; требует исправления до утверждения
- **[РЕКОМЕНДАЦИЯ]** — улучшение, которое не блокирует принятие плана

## Формат замечания

```
### [ID] [Краткое описание]

- **Критерий:** A / B / C / D / E
- **Серьёзность:** [КРИТИЧНО] / [ВАЖНО] / [РЕКОМЕНДАЦИЯ]
- **Место в плане:** Блок N, пункт N.M (или «Общий»)
- **Описание:** [Что именно не так]
- **Связано с:** `[документ или файл]`, раздел / строка (если применимо)
```

ID формировать как `A-001`, `B-002` и т.д. (буква критерия + трёхзначный номер).

## Что не входит в задачу

- Написание кода
- Код-ревью
- Функции планирования (декомпозиция, оценка усилий) — это задача `make-plan`
- Стилистические правки в `implementation-plan.md`

## Как делать

Не вычитывай файлы, это сделают субагенты. Ты выступаешь в роли **супервизора**. Следуй циклу:

### Итерация ревью

**Шаг 1 — Запустить субагента-ревьюера**

Запустить субагента (Agent tool) с инструкцией провести ревью. Передать ему содержимое этого файла **от начала и до строки `## Как делать` — не включая её**. Также передать:
- ссылку на файл `implementation-plan.md`
- ссылку на файлы `feature-spec.md`, `functional-spec.md`, `ui-spec.md` (если существуют)
- путь к кодовой базе для проверки критерия D
- инструкцию вернуть в ответе общее количество выявленных недостатков с группировкой по важности.

Субагент должен записать результат в `implementation-plan-review.md`, используя шаблон из `references/review-template.md`.

**Шаг 2 — Проверить наличие критических замечаний**

На основе статистики от субагента-ревьюера:

- Если критических замечаний нет — перейти к **Завершению**.
- Если критические замечания есть — перейти к Шагу 3.
- Самому в файлы лезть не нужно, это работа субагентов.

**Шаг 3 — Запустить субагента-исправителя**

Запустить субагента (Agent tool) с инструкцией устранить выявленные недостатки. Передать:
- ссылку на файл `implementation-plan.md`
- ссылку на файл `implementation-plan-review.md`
- указание: исправить все замечания с меткой `[КРИТИЧНО]` и `[ВАЖНО]`; замечания `[РЕКОМЕНДАЦИЯ]` — на усмотрение

Субагент обновляет `implementation-plan.md` в соответствии с замечаниями.

**Шаг 4 — Удалить файл ревью и начать новую итерацию**

Удалить `implementation-plan-review.md`. Вернуться к Шагу 1.

### Завершение

Когда критических замечаний не осталось:

1. Сообщить пользователю: сколько итераций прошло, какие замечания остались (только `[ВАЖНО]` и `[РЕКОМЕНДАЦИЯ]`).
2. Спросить: «Принимаете план или отправить на доработку к шагу make-plan / make-research?»
3. Ждать решения человека. Не коммитить, не выводить commit message.
